## 总体结论

**建议：打回，修完致命与重要项后再定稿。** 方案整体架构选择（双端插件、回收站式硬删、storage-domain 写回取消归档）方向正确，回收站选址、路径重算、storage-domain `get`+`global.set` 路径的 spike 均是合理且到位的设计功夫；但暴露了一个未做鉴权/CSRF 防护、却承载"真实移动用户会话文件"高危动作的 HTTP 路由面，且错误契约在输入校验、并发、partial-failure 处留有多处会让测试设计无从下手的空白。这两类不补，方案不足以进入测试设计阶段。

## 一、致命

### F-1 高危删除路由无鉴权、无 CSRF 防护，且返回路径信息泄密
- **位置**：INTERFACE.md §3（`/sm/api/delete`、`restore`、`emptyTrash`、`unarchive`）；PLAN.md §2.1、§5.4「栅格 2」所谓保障句（"路由为内部同源自用，不做鉴权面外延"）；BRIEF.md §8「密钥/登录态：无」。
- **为什么是问题**：BRIEF §8 的"无鉴权必要性"论证完全依赖"同源自用、外部不可达"这一未经验证的**前提**。方案从没回答两个决定生死的问题——
  1. **网络面**：`ctx.webServer`/host webserver 监听地址是什么？只绑 127.0.0.1 还是可能绑 LAN/0.0.0.0？若绑定非 localhost（DSH 需要提供给局域网设备或本地多进程访问），任何能触达该 origin 的无害脚本/网页都能 `POST /sm/api/delete` 把人**真实会话目录拖进回收站**（不可直接读取正文，但可执行等价删除），或 `GET /sm/api/trash` 读回 `originalDir` 绝对路径。
  2. **同源失守面**：即使只绑 localhost，同源也意味着任何能在这个 origin 上注入 JS 的入口（XSS、其它用户已装的插件、同一 webserver 站点的其它页面）都天然拥有此删除能力，方案把它当成"无鉴权是安全的"来声明。
  3. **CSRF**：`emptyTrash`/`delete`/`restore` 均为 `POST` 且副作用不可逆（清空/移动真实文件），却没有 Origin / `Sec-Fetch-Site` 头校验、无一次性 token、无 State-changing 的幂等性之外的防护。`Content-Type: application/json` 只挡住朴素 form 提交，挡不住 `fetch` 与 `text/plain`。BRERIEF 说自己"三问必答"，但对"路由面怎么保证只有可信 client 能调"这一问没有实质回答。
  - 附带：`GET /sm/api/trash` 把 `originalDir`（含 `~/.dsh/sessions/<cwd-slug>/<id>` 的用户路径与 cwd 信息）无鉴权读出，是不必要的信息暴露，正好和 F-1 叠加。
- **怎么改**（方案层，不改源码但须把保障写进契约）：
  1. 在 INTERFACE §4 增补**网络面契约**：明确声明 `webServer` 仅监听 loopback（并可加"拒绝非本机来源请求"），把"只 bind 127.0.0.1"写成硬性验收项与发布 gate 检查项。
  2. 给所有 `POST` 写路由加 **Origin / `Sec-Fetch-Site` 校验**：host 收到写请求先比对 `Origin`（或 `Sec-Fetch-Site`) 必须为 `same-origin` / 本机 origin，否则 `403`。此校验属接口契约的一部分，写进 §3 顶部统一约定。
  3. 删除/清空这类不可逆高危动作，除 `confirm:true` 外，host 侧再验一次同源头（§3.3 已要求 confirm，但 confirm 本身是 client 可伪造的字段，不能替代同源校验）。
  4. `GET /sm/api/trash` 返回值去掉 `originalDir`（或改为内部 id，路径仅留存 host 内存），避免路径信息泄密。
  - 说明：这一条同时改写 BRIEF §8 的"无密钥=无鉴权面"结论——**不碰密钥 ≠ 无需鉴权**，前者是横向信任（不读外部），后者是宿主安全（防止被同一 host 上的恶意进程/跨源面滥用），两者独立。

## 二、重要

### I-1 错误契约缺失具体输入边界，测试反向用例无据可依（必查项①）
- **位置**：INTERFACE.md §3.1/3.2/3.4 对 `id`、`cwd` 的校验未定义；§0 虽给了三类错误码顶层约定，但每个入口没有列明对**非法输入**返回什么。
- **为什么是问题**：测试设计代理"不看实现也能照写测试"，但非法输入（`id` 为空串/含 `/`、`..`/超长/非 string；`cwd` 含路径穿越、指向 sessions 外；`title` 超长；`unarchive`/`restore` 的 `id` 非法）没有任何预期，反向用例只能瞎猜——这正是必查项①要抓的失职。
- **怎么改**：每个入口补一张「输入校验」子表：对 `id` 非 string/含路径分隔符或 `..`/空串→返回 `{ok:false, code:"invalid-id"}`（新增稳定 code，纳入 §0 的 `user-backend-error` 家族）；`cwd` 解析越界→现有 `path-out-of-bounds`；并对"cwd 缺省"到底返回哪个 code 明确化（现在只写"报错"，没说 code）。

### I-2 restore 的幂等语义与"已存在于原路径"存在歧义，且恢复可能覆盖同名新目录（数据丢失面）
- **位置**：INTERFACE.md §3.2（"回收站无该项→not-in-trash"；"目录已在原路径→ok:true"）。
- **为什么是问题**：两个断言缺乏判定依据——host 如何区分"不在回收站"与"已恢复回原位"？更危险的是：原路径若在删除后被**重建了一个同名/id 会话**（新会话 id 通常唯一，但同一目录路径下有同名目录完全可能），`restore` 把回收站目录 `mv` 回原路径时，`rename` 对已存在目标的行为（覆盖 / 报错）未定义。若采用覆盖，恢复会**整体覆盖新会话**，造成真实数据丢失；测试无从断言。
- **怎么改**：INTERFACE §3.2 明确定义判断顺序（先查回收站记录是否存在 → 存在则检查原路径是否已被占 → 被占用返回新 code 如 `restore-target-exists` 并**不移动**，提示用户），并写明 `rename` 在目标已存在时的契约（显式拒绝而非覆盖）。恢复绝不覆盖既有目录。

### I-3 delete/恢复过程中的 partial-failure 数据一致性（删除已归档会话 = 两步）
- **位置**：PLAN.md §5.1 风险3 只覆盖归档集写回的自身失败；但 PLAN.md T3 / §5.2 的"删除已归档会话 = 先移文件、再从 archivedSessionIds 移除 id"是**两步操作**，INTERFACE §3.1 对这两步间的中途失败无契约。
- **为什么是问题**：文件已入回收站、归档集写回失败（storage 故障）→ 会话消失了、归档视图却仍显示幽灵项；反之集合已清、文件移动失败 → 文件仍在但 id 已从归档集移除（该会话在正常列表也不可见——它已归档，归档集合却没了它）。方案既没定义该 partial state 的判定，也没定义恢复动作（重试写回？）。
- **怎么改**：在 INTERFACE §3.1 明确"删除已归档会话"的**结果契约**：若第二步行存储写失败，delete 应返回 `system-error`（而非 `ok`），并声明 host 保证"归档集合回滚或重试"，且测试对"文件已移走+集合未清"的中间态有明确预期（列表中消失但归档视图仍显示 → 再次触发删除应为幂等补齐集合清理）。

### I-4 host 侧无运行中会话保护，运行中删除会造成 flush 分裂（client 拦截是唯一防线）
- **位置**：INTERFACE.md §3.1 delete；PLAN.md §5.2 风险6（缓解仅说"client 拦截 + 尽力而为"）。
- **为什么是问题**：运行中拦截全交给 client（软防线）。绕过 client 直调 `POST /sm/api/delete`（比如另一脚本、或同源注入）、或 client 的 `running` 判断因列表 phase 不新而失效时，host 会把正在 flush 的会话目录移走，运行中 Session 续写到新位置 → **日志分裂 / 丢尾**。对"移走用户真实数据"的高危路由，不能只靠前端拦截。INTERFACE §3.1 完全没提 host 侧对运行中会话的降级。
- **怎么改**：INTERFACE §3.1 增加 host 侧护栏：delete 前校验目标会话是否正被 host 占用/写入，占用则返回稳定 code（如 `session-running`）并**不移动**；`GET /sm/api/trash` 只回显已确认落盘条目。至少把"host 拒绝在运行时被删"写成契约，让测试能断言直调 API 也被拦。

### I-5 归档会话的"删除"入口缺失，导致声称支持的路径实际不可达
- **位置**：PLAN.md T3（"删除已归档会话时先移文件再移除 id"）、INTERFACE.md §2.4 场景「归档视图打开期间删除某归档会话（走了删除流程）」；对照 INTERFACE §1.1（删除按钮只出现在**非 blank、非 running** 的**正常列表**行上）与 §2.3（归档视图只有「取消归档」按钮）。
- **为什么是问题**：已归档会话被官方 `sessionVisible` 过滤，**不会出现在正常列表**，因此删除按钮对它们不可见；而归档视图只有「取消归档」没有「删除」。于是 PLAN/INTERFACE 反复提到并为之写了两步写回逻辑的"删除已归档会话"，用户在 UI 上根本无从触发——要么需求/BRIEF 没要求，要么实现漏了归档视图的删除入口。这是需求-方案的责任漂移：方案造了一条没人能走的路。
- **怎么改**：先与需求定稿对齐——若 BRIEF 确实不要删除归档会话，则删掉 PLAN T3 与 INTERFACE §2.4 里这块分支（避免死代码/测试幻影）；若要支持，则在归档视图行上加「删除」按钮（同样走 10 秒撤销/回收站），并在 INTERFACE §2.4 为它补错误契约。方案当前状态是"两者都写了一半"，必须二选一，不可悬置。

### I-6 SPIKE 关键假设的降级方案本身就是它判定的坏方案（必查项②）
- **位置**：SPIKE-UNARCHIVE.md §2 路径 C、§4「兜底」；PLAN.md §5.1 风险4。
- **为什么是问题**：主路径（`ctx.storageDomain.get("workspace").global.set` 触发端到端广播）被 SPIKE 诚实标为"**待实机确认的设计假设**"。可一旦实机假设不成立，方案给出的兜底是"退化路径 C（直接改 `workspace.json` 文件）+ 客户端 refresh() 兜底"。而路径 C 在 SPIKE §2 自己就列了三条罪状：不触发 `domain/changed`、不广播、违反 invariant、**内存↔文件双写分歧**。也就是说唯一的紧急降级，正会制造它本想避免的架构缺陷——降级不是 rescue，而是换一种方式崩。必查项②要求评估降级方案是否足够，此例不足。
- **怎么改**：降级方案不能停留在路径 C。须把**端到端实机验证提前到方案阶段**：用最小双端插件 node 半在真实 dsh host 上确认 `get("workspace")` 拿得到 live 句柄、广播能达（这正是 SPIKE 唯一没验证但依赖最重的一环）。若确认主路径不可行，需在方案里给出第三条"正规"路径（如经 host 已有的 RPC/event 通道二次触发广播，或与官方 workspace 域保持内存一致性后再落盘），而不是退回直接改文件的路径 C。**在 spike 补测之前，取消归档这条核心功能链路不应被当作可定稿。**

## 三、建议

### A-1 `id` 来源可信度只防了绝对路径，没防编码逃逸
- **位置**：PLAN.md §5.1 风险1（"host 用 DSH 编解码函数重算路径，不接受任意绝对路径"）。
- **为什么**：方向对，但 `id` 本身由 client 传入，`encodeSegment` 是否对 `..`/`/`/空净化未在方案层说明。若某 id 段能逃逸出项目目录，`mv` 可能移错。
- **怎么改**：在 INTERFACE §3.1 明确 host 对 `id` 做 `encodeSegment` 后结果等于编码前输入（无逃逸）的校验，并断言目标目录在 `projectDir(root,cwd)` 前缀内（`path-out-of-bounds` 覆盖到 id 段）。已有路径前缀思想，补一层 id 净化断言即可。

### A-2 错误响应的 HTTP 状态码未约定
- **位置**：INTERFACE.md §3 顶部（只说"响应一律 `{ok:true}` 或 `{ok:false}`"）。
- **为什么**：测试脚本直接调用，不知道非法输入/未鉴权到底是 200+`ok:false` 还是 4xx/5xx；混合两种风格测试就得拍脑袋。
- **怎么改**：补一条全局约定：合法请求一律 200 + `{ok:...}`；**违反契约的请求（缺 body/非法 JSON/缺鉴权头/`confirm` 缺失）返回 4xx**（400/403），这样错误契约与 HTTP 语义对齐，测试反向用例有确定依据。

### A-3 存储域写回的并发契约只覆盖了 unarchive，没覆盖 restore 的并发重叠
- **位置**：INTERFACE.md §4「并发」行与 §3.2。
- **为什么**：§4 覆盖 delete/unarchive，但 restore（两客户端同时恢复同一会话，或 delete→restore→delete 交错）没有幂等/串行说明；叠加 I-2，正好是数据丢失高危点。
- **怎么改**：在 §4 并发行补 restore 的规则（以回收站记录是否存在为串行真值，同一 id 的 restore 串行执行、后写幂等）。

### A-4 需求原话的"10 秒后自动清空"与方案定稿的"永久保留到手动清空"不一致
- **位置**：BRIEF.md §3 F1「回收站清空策略（10 秒后自动清空 / 保留待手动清空 / 定期清理）方案阶段定」；PLAN.md §7。
- **为什么**：BRIEF 把策略列为待定，PLAN 定稿为"到期保留目录、仅手动清空"，这是合理的下切（避免 10 秒自动 rm 造成不可恢复瞬时丢失）。方向没问题，但**两个文档读者会看到两种口径**，且 BRIEF 成功标准第 3 条"倒计时结束→会话被真实删除（文件移入回收站，从列表消失且重启后不复现）"对"仍在回收站目录、只是不在 UI"是否满足"真实删除"存在歧义。
- **怎么改**：把 PLAN §7 的口径回写到 BRIEF §3 或加一句"回收站=软删除，重启不显示，手动清空才是硬删"，消除跨文档口径差。

### A-5 删除当前选中会话的 UI 态契约缺失
- **位置**：PLAN.md §5.2 风险5（缓解"client 调 clear() 或选下一个"）；对照 INTERFACE §1.4 错误契约表。
- **为什么**：风险5 承认"删除当前会话后 UI 停 no-session 态"，但 INTERFACE §1.4 完全没有对应行，测试断言不了。
- **怎么改**：在 INTERFACE §1.4 补一行"删除当前选中会话 → UI 回到 no-session（或自动选中相邻会话）"的明确预期；若采用 clear()，需在撤销恢复后回到什么态也定义清楚。

## 审查结论一句话

方向与主要架构决策成立，但致命的高危路由无鉴权/CSRF 面 + 错误契约与并发/partial-failure 的多处空洞，加上 SPIKE 降级方案自相矛盾，**不足以定稿，需按 F-1 + 六条重要项修完再进入测试设计**。
