## 致命（必须改）

### F1 — G1 的因果链自相矛盾：spike S1 的"好结果"等于"零收益"

**位置**：§1.4 G1（第 60 行）、§4 T0.2（第 453 行）、§5 R4 失败模式 1（第 525 行）、§5 R8 S1（第 561 行）

**问题**。G1 把治理手段分成两条分支：

- 首选：直接删 `background-attachment: fixed`。前置条件写的是"DSH web 的滚动容器是内层 div 而不是 document
  —— 若 body 本来不滚，删掉它**视觉零变化**，这是最短的修法"。
- 备选（body 真在滚时）：改用 `position:fixed` 专用背景层。

这两句连起来读就露馅了：**如果 body 本来不滚，那 body 上的 fixed 背景本来就不需要每帧重绘**
（背景相对视口固定，视口不动、body 不滚，这个背景不参与内层滚动容器的绘制循环）。
所以"删掉它视觉零变化"和"删掉它性能零收益"是**同一个前提推出来的同一件事**。
在这个分支下，G1 什么都没修——它只是让静态断言 P1 变绿了。

反过来说：如果 §3 C 类的结论（5 套皮肤 fixed 大图是滚动卡顿主因）是真的，那 body **必然在滚**
（或者滚动容器的祖先链上也有 fixed 背景），S1 的结论只能是"走备选"。
**方案同时相信"fixed 是主因"和"body 可能不滚"，这两条不能同时成立**，而方案没有识别这个矛盾。

**为什么这是致命的**。G1 是 BRIEF 成功标准 4（滚动不卡）的第一治理手段，占了性能战线的一半权重。
如果 S1 跑出"body 不滚"，方案给出的路径是走首选、删 fixed、P1 变绿、门禁全过——
**然后交付一个滚动照旧卡的版本，而所有自动化验收都是绿的**。
P9（真机帧率）是唯一能发现这件事的口径，而它明确"不作为门禁"（第 440 行）。
换句话说：方案在这条路径上失去了发现自己没修好的能力。

**怎么改**（三处联动）：

1. **T0.2 的 spike 改成归因实验，不只是查滚动容器**。查滚动容器只能回答"删了会不会变丑"，
   回答不了"删了会不会变快"。最小实验要采三组帧时间：
   ① 未应用皮肤基线；② 应用 blue-fantasy；③ 应用 blue-fantasy 后在 devtools 里手动
   把 `body { background-attachment }` 改成 `scroll`。
   只有 ②③ 有显著差值，才证明 fixed 是根因、G1 值得做。同时开 devtools 的 Paint flashing /
   Layers 面板看滚动时整视口是否闪重绘区，这比数字更直观。
2. **S3（rAF 采样脚本可行性）必须提前到阶段 0，与 S1 合并**。因为上面这个实验需要它，
   而现在 S3 挂在"P9 能否量化"名下、没有排入阶段 0 任务表（T0.1/T0.2/T0.3 三项里没有 S3）。
   顺序颠倒了：测量能力是决策的前提，不是验收的附属品。
3. **补第三条分支**：若归因实验显示 fixed 不是主因，PLAN 必须写明下一步查哪里
   （候选：内层滚动容器自身或其祖先的 fixed 背景 / `backdrop-filter` 元素数 / 大图 decode
   与 `background-size: cover` 的每帧缩放）。现在方案只有"首选/备选"两个分支，
   缺"根因定位错了怎么办"，而这是最需要预案的一支。

顺带一句：S1 的方法本身没写错（元素的 `scroll` 事件不冒泡，所以"在 document 上挂监听看是否触发"
确实能区分 document 滚动与内层 div 滚动）。问题不在方法的正确性，在它回答的**不是** G1 需要的那个问题。

**没有发现第二条致命问题。** 依赖方向单一（client → panel → api，无反向）、无循环依赖、
storage 零迁移是本方案最稳的一处决策，不硬凑。

### I1 — 面板懒挂载引入的状态归属漏洞：试穿态卸载时怎么办，方案一个字没写

**位置**：§1.2（第 36-38 行）、§3.3 E3（第 215 行）、§3.3 T4 / S2、§3.8 第 2 条（第 383 行）

**问题**。T4（`previewCustomTheme`）和 S2（`previewSkin`）是刻意不写 storage 的**纯内存 + DOM 态**
（§3.5：「preview / 试穿刻意不写键」）。旧架构里槽位条目常驻，试穿态的生命周期没人关心。
新形态下面板会被**卸载**（E3 关闭、切换 section），于是出现一个旧架构不存在的问题：

> 用户试穿了皮肤 A（未应用）→ 点「返回」关闭面板 → 现在页面是什么样子？

两种可能，方案都没选：
- 试穿态挂在面板组件的 effect 上 → 面板卸载即撤销试穿。用户体验：点「返回」外观突然跳回去。
- 试穿态挂在 `apply(ctx)` 层 → 试穿残留。用户体验：关了面板页面还是试穿的皮肤，刷新后又变回原样，
  且此时 8 个 storage 键与页面实际外观**不一致**，E1 摘要显示的是 storage 里的旧值——摘要与眼见不符。

§3.3 E3 的断言只写了"关闭前后 8 个 storage 键的值完全相同"，这一条**在两种实现下都成立**，
所以测试根本挡不住这个分歧。§3.8 第 2 条讲的是"试穿执行失败时的回滚"，不是"试穿成功后面板被卸载"。

**顺带暴露一个更硬的问题：皮肤引擎创建在哪一层，方案自相冲突。**
§2.1 写 `panel-skin.js` 的内容包含「引擎接线」（第 98 行），
但 §3.2 又要求启动时（`apply` 阶段、面板必然未打开）就 `activateSkin` 恢复用户皮肤（第 203 行），
并且 `ctx.effect` 的 disposer 要调 `teardownSkins()`（第 204 行）。
如果引擎真的建在懒挂载的 panel-skin 里，**启动恢复直接失效**——用户刷新页面后皮肤不生效，
必须手动打开面板才恢复。那就撞穿 BRIEF 成功标准 3（升级后不丢当前选择）。

**怎么改**。在 §3.3 前面加一段「状态归属表」，把三类状态各自的宿主写死，一句一条：

| 状态 | 归属 | 生命周期 |
|---|---|---|
| 引擎实例、`__SKIN_MANIFEST__` 注册表、启动恢复、`teardownSkins` | `apply(ctx)` 层（`client.js`） | 与插件同生命周期，与面板开关无关 |
| `open` / `section` / 搜索词 / 勾选态 / 错误文案 | 面板组件 | 面板卸载即丢（明确接受） |
| **试穿态** | 建议归 `apply(ctx)` 层，但面板卸载时**主动撤销** | 需要方案明确拍板 |

我倾向"面板卸载时撤销试穿"：试穿的语义本来就是"看一眼"，关掉面板还留着反而让 E1 摘要说谎。
定了之后 E3 补一条断言：「关闭面板后 `getPreviewState()` 为空，且 body 外观与 storage 记录一致」——
这条断言在两种实现下结果不同，才挡得住。

### I2 — `createThemePanel(deps)` / `createSkinPanel(deps)` 的 deps 契约完全缺失，且 §3.9 指向了一处不存在的内容

**位置**：§1.1 D4（第 25 行）、§2.1（第 95-98 行）、§3.9 最后一行（第 407 行）

**问题**。D4 是整个 UI 拆分的核心决策，两个工厂函数是新写的（不是"沿用"，无法拿旧用例断言）。
但 `deps` 里到底有什么，全文没有任何一处定义。§3.9 写「`createThemePanel`；`createSkinPanel`（新增，
签名见 3.11 断言）」——**翻到 §3.11 是 P1-P9 性能口径表，里面没有任何签名断言**。指路指到空地。

后果很具体：§1 开头承诺"第 3 节全文另存为 INTERFACE.md（测试设计唯一输入）"，
而测试方拿着这份 INTERFACE **写不出这两个新模块的任何单测**——不知道传什么进去、返回的组件吃什么 props。
T2.3 里 `entry-lazy.test.mjs` 要用 fake React 挂载面板，第一行就卡住。

**怎么改**。§3.9 补上确切签名，`deps` 逐字段列出（不许写"等等"）。例如：

```
createThemePanel({ React, themeApi, customThemeApi, onBack }) -> { Panel }
createSkinPanel({ React, engine /* 可为 null */, customSkinApi, onBack }) -> { Panel }
```

同时明确两条边界约束（这是 D4 真正要买的东西，不写就白拆）：
1. 两个 panel 文件**不得** import / 引用 `client.js` 的任何标识符（拼接后同作用域，物理上拦不住，
   只能靠约定 + 一条 grep 断言）。
2. `Panel` 是**组件引用**，只经 `React.createElement` 挂载——R2 失败模式 2 已经识别了这个坑，
   但约束写在风险清单里、没写进接口契约，测试方看不到。搬到 §3.9。

顺带：`engine` 可为 `null` 这件事要写在签名里（见 I6），否则 panel-skin 的降级分支无从测试。

### I3 — 体积门禁的两个数字既是"死断言"又是"待实测"，自相矛盾

**位置**：§1.4 G3（第 62 行）、§3.10 体积门禁（第 422 行）、§3.11 P5（第 436 行）、§4 T3.4（第 480 行）、§5 R5 失败模式 3（第 538 行）

**问题**。四处口径打架：

- G3 / §3.10 / P5：`lib/client.js` ≤ **716800 B**、4 图 base64 合计 ≤ **307200 B**，并加一句
  「门禁数值只准下调，不准上调」。
- T3.4：「按实测值把 `build.mjs` 的两个上限写死（**先做后定**，不预设不可达的数）」。
- R5 失败模式 3：「压完仍达不到 700 KB → 门禁数值在 T3.4 按实测落定」。

也就是说：压不到 700 KB 时，处置办法是**把门禁调大**——直接违反"只准下调"。
而 716800 这个数并非实测得来，是从"1219 KB → 目标 700 KB"倒推的愿望值。
INTERFACE 是测试设计的唯一输入，测试方会照 P5 写死 716800，实施到 T3.4 一改就红，
然后所有人开始怀疑"门禁到底算不算数"——这是门禁公信力被自己搞坏的经典路径。

**怎么改**：
1. §3.10 / §3.11 里这两个数标成 `TBD(T3.4 落定)`，同时给一条**不可协商的兜底上限**
   （比如「无论实测多少，`lib/client.js` > 900 KB 就不许收工，必须走 S2 资源外置或换图」）。
   兜底上限才是真门禁，目标值是目标值，两者别混。
2. "只准下调"改成"**T3.4 落定之后**只准下调"，并在 build.mjs 里把数字旁边写上落定日期与实测值来源。
3. G3 的预期效果那一栏（"~773 KB → ≤300 KB"）注明这是**估算**，WebP 对已经是 JPEG 的照片类素材
   通常只有 25%-35% 的收益，对大面积渐变/插画可能更多——把"没达标"当正常结果对待，别当例外。

### I4 — 并发与重复操作面完全缺失：applySkin 是 async + Blob-URL 注入，连点两次的语义没人定义

**位置**：§3.3 S2/S3/S4、§3.7 最后一段（第 353 行）、§3.8 第 2-3 条

**问题**。§3.7 明确激活流程是「把 `bundleText` 作为 Blob-URL 经典脚本注入执行，
再 `modules.import(pkg)` 取 `apply`」——脚本注入天然异步，`importCustomSkin` / `applySkin` 也都标了 async。
但方案对下列场景一个字没写：

1. 用户在皮肤 A 还在注入的过程中点了皮肤 B（卡片列表里点两下很容易）。两条激活流程交错：
   A 的 `restoreSnapshot(body)` 快照是在 B 已经改过 body 之后拍的、还是之前？
   disposer 逆序执行时会不会把 B 的清理跑在 A 的注入之后？§3.8 第 2 条只覆盖"单次失败的回滚"。
2. 重复点同一个「应用」按钮两次 —— 同 id 是否会二次注入脚本、`modules.invalidate` 时机如何。
3. 试穿 A → 直接应用 B（不先取消试穿）—— 试穿态的清理与新皮肤的注入谁先谁后。

这三种都是用户 5 秒内就能触发的操作序列，不是极端场景。而且症状会是"偶发的样式残留 /
切皮肤后卸不干净"，最难查的那一类。

**怎么改**。在 §3.3 皮肤段表格后加一段「串行化约定」，最省事的写法就够：

> 同一时刻只允许一个激活流程。`activateSkin` / `previewSkin` / `applySkin` 进入时若已有流程在跑，
> **忽略本次调用并直接 return**（不排队、不抛错），UI 侧按钮在流程中置 disabled。
> 试穿态在新的激活流程开始前先撤销。

配一条单测：连续 `await Promise.all([applySkin('a'), applySkin('b')])`，
断言最终 body 状态与 storage 一致且只有一套皮肤属性/style 残留。
一个布尔闸 + 一条断言，比事后查残留便宜得多。

### I5 — a11y CSS 是安全闸上的一个明确豁免口，且 R11 的"不新增外部网络请求"保证兜不住它

**位置**：§3.7 容量与数量（第 335 行）、§3.7 入口说明（第 312 行）、§5 R11 第 1 行（第 580 行）

**问题**。三件事叠在一起：

1. §3.7 明写「体积：`base64(skin.json + client.js)` ≤ 262144。**`a11y.css` 不计入**」——
   a11y 文本**没有任何长度上限**，却和 `bundleText` 一起全文存进 `skin-gallery-custom-v1`。
   localStorage 通常 5 MB 上限、且是**整域共享**的。一份 4 MB 的 a11y 文本能把整个域的
   localStorage 顶爆，连带把用户已导入的主题/皮肤写不进去（§3.8 第 5 条的"写静默忽略"降级会静默吃掉这个失败，
   用户看到的是"导入了但没保存"）。这与 BRIEF 敏感面"不丢用户已导入的自定义主题与皮肤"直接冲突。
2. a11y CSS **没有任何内容校验**（12 条黑名单是对 `client.js` 的，§3.7 第 324 行明说"`client.js` 静态契约"）。
   CSS 是能发网络请求的：`@import url(https://evil/x.css)`、`background: url(https://evil/beacon?...)`。
   注入进 `<style>` 就会执行。
3. 而 R11 第 1 行声称"不新增外部网络请求"的保证手段是"`src/**` 与 `lib/client.js` 中不出现 `fetch(` /
   `XMLHttpRequest` ..."——**只审了自家代码，完全没覆盖用户导入内容这条路径**。
   保证的措辞（"不新增外部网络请求"）比实际兜住的范围大。

**信任边界也没写清**，这是更根本的一点。§3.7 的 12 条黑名单是**纯子串匹配**，
而导入的 bundle 是以经典脚本在主页面同源执行、拥有全部页面权限。这个闸挡得住手滑和明显的坏活，
挡不住稍微绕一下的（`indexedDB`、`new Worker(`、`navigator.sendBeacon`、`caches`、`top.location`
都不在名单上；`window['ev'+'al']` 这类拼接也不在）。方案把它列在 R11 的"保证手段"栏里，
读者会以为这是沙箱。它不是。

**怎么改**（三条都不难，且不违反"契约不得放松也不得收紧"——**加上限和写声明都不是放松安全闸**）：

1. §3.7 给 `a11y` 补契约：必须是字符串或缺省（其他类型 → `ERR_SKIN_MISSING_FILE` 或新码，
   但既然错误码表不许动，用现有码即可）；长度上限写死（64 KB 足够 a11y 用）；
   超限 → `ERR_SKIN_SIZE`。这是**新增约束**，需要跟 navigation-diary 那份实测数据核一下不会误伤
   （已知 raw 93580 B 是 client.js，a11y 大小 PLAN 未记录，T0 阶段量一下）。
2. a11y 文本注入前至少拒 `@import`（一条子串匹配）。`url()` 要不要拦是权衡——
   皮肤合法用途也可能用到 data URI 的 `url()`，可以只拦 `url(` 后跟 `http` / `//` 的形态。
3. §3.7 末尾加「信任边界声明」，把上面那段"同源全权限、黑名单是防手滑不是沙箱、已知未覆盖的 API"
   逐条写下来。同时把 R11 第 1 行的保证措辞改成两句：
   「**包内代码**不发起外部请求（可静态断言）；**用户导入的 client.js / a11y.css** 在同源上下文执行，
   其网络行为不受本插件约束——这是已知且刻意保留的既有契约边界。」
   诚实的声明比虚高的保证有用：后者会让下一个人以为这里已经安全了。

### I6 — 引擎不可用（`__DSH_MODULES__` 缺失）时，S5 / S7 / S8 的行为未定义

**位置**：§3.2 第 3 行（第 202 行）、§3.3 皮肤段 S5 / S7 / S8

**问题**。§3.2 定了降级语义：引擎为 `null`，皮肤区渲染一行占位文案，不抛错、不影响主题区。
但 §3.3 的皮肤段 8 个入口全都隐含依赖引擎，其中三个的降级行为是空白：

- **S7 导入皮肤**：契约说"校验通过 → 写 `skin-gallery-custom-v1` + **bundle 注册进引擎 manifest**"。
  引擎为 null 时，注册那步做什么？跳过（那 storage 写了但引擎不知道，等于半提交，
  与 §3.8 第 1 条"先全量校验通过再 commit"的原子性承诺冲突）？还是整个导入拒绝（返回什么码）？
- **S5 恢复默认外观**：`clearSkin()` + `restoreDefaultSkin()`。前者是引擎方法，后者是 storage 方法。
  引擎 null 时是只做后者，还是整条不可用？
- **S8 删除皮肤**：若删的是 applied 项要"卸载皮肤"——引擎 null 时这步怎么办。

按 §3.2 的口径（皮肤区只渲染占位文案），最合理的答案是"这三个入口在引擎 null 时压根不可达"。
如果是这样，就把它写出来 —— 一句"引擎为 null 时皮肤段只渲染占位文案，S1-S8 全部入口不渲染、不可调用"
就把三个空白一次填满，测试也好写（断言占位态下不存在这些按钮）。
现在的空白会让实现者各自猜，而这是"半提交"这类脏状态的常见来源。

### I7 — 覆盖同 id 皮肤（尤其是正在应用的那个）行为未定义

**位置**：§3.7 数量与容量（第 336 行）、§3.7 落盘形态（第 353 行）、§3.3 S7

**问题**。方案写了"覆盖同 id 不受数量限制"、"重新注册同 id 前先 `modules.invalidate(pkg)`"，
也写了"导入成功不改变当前外观"。这三条在**覆盖当前已应用的皮肤**时会打起来：

用户 applied 了自定义皮肤 X → 改了 X 的 `client.js` → 重新导入同 id 覆盖。
结果：`skin-gallery-custom-v1` 里的 `bundleText` 是新的，但页面上跑的还是旧 bundle（已执行过，
DOM 已改），且"不改变当前外观"意味着不重新激活。用户看到的是"导入成功了但页面没变"，
刷新才生效。这不是灾难，但它是**registry 与实际渲染态不一致**的漏态，也是最容易被反复报为 bug 的那种。

顺带：这正是自定义皮肤开发者（比如 navigation-diary 那类外部交付方）的主循环
——改代码、重新导入、看效果。所以这个路径的体验值得定清楚。

**怎么改**。§3.3 S7 加一行契约，二选一并写死：
- 方案 a（推荐）：覆盖的 id **恰好是当前 applied/preview 的那个**时，导入成功后**自动重新激活**
  （`invalidate` → 重新注入 → `activateSkin`）。此时"不改变当前外观"这句要改成"不改变**选中的** id"。
- 方案 b：保持不重激活，但 UI 明确提示"已保存，刷新后生效"。

无论选哪个，都补一条断言：覆盖 applied 的 X 之后，`bundleText` 是新的，
且（a）body 上生效的是新 bundle 的标记 /（b）明确断言仍是旧的且 UI 有提示。

### I8 — `lib/invariant.js` 是手工产物，与 §3.10"不存在任何手工维护的产物"及 BRIEF 硬约束直接矛盾

**位置**：§2.1（第 104 行）、§2.2 末（第 125 行）、§3.10 唯一产物（第 421 行）

**问题**。§2.1 写 `lib/invariant.js  # 占位，沿用现状（export function apply(){}）`。
§2.2 只说 build.mjs 一并写出 `lib/client.js` 与 `lib/index.js`，**没提 invariant.js**。
于是它就是一个手工维护的产物文件——而 §3.10 的断言明写「`lib/` 下……**不存在任何手工维护的产物**」，
BRIEF 硬约束也正是"`pnpm -r build/check` 不得再静默摧毁手工产物"。方案一边宣布手工产物"自然消失"
（D6 理由栏），一边在目录树里留了一个。

**怎么改**。先回答一个问题：**这个文件有消费者吗？** 方案只说"占位，沿用现状"，没说谁在读它。
- 如果 loader / cordis 需要它存在 → 让 build.mjs 生成它（三行代码），断言才立得住。
- 如果没人读 → **直接砍掉**。"沿用现状"不是保留理由，尤其是在一次以"删三个包"为主题的合并里。

同样的话适用于 `src/index.js`（"node 半边占位"）：如果 cordis 要求包有 node 半边就留，
方案里给一句依据；如果只是"三份旧 index.js 合一"的惯性，那合出来的是一个空函数，值得问一句它存在的意义。

### I9 — 缺"打开设置→通用、以及面板打开后滚动"的验收口径，而这正是 BRIEF 的用户原话场景

**位置**：§3.11 P1-P9（第 430-440 行）、BRIEF 成功标准 2 与 4

**问题**。BRIEF 引了用户原话："我打开设置、通用时上下滑动查看时不卡"。方案给的 9 条口径分布是：
P1-P5、P8 测皮肤资源的静态指标；P6 测 JSON.parse 次数；P7 测 `open=false` 时的首屏节点数；
P9 测**应用皮肤后全页**滚动帧率。

漏了两块，都在用户描述的场景正中间：

1. **面板打开之后的滚动**。P7 只断言 `open=false` 节点数 ≤10，以及 `open=true` 后卡片"出现"。
   用户真正会做的事是：点开面板 → 上下滑动看 15+9 张卡。这个状态下的表现**零口径**。
   §1.4 明确"不做列表虚拟化"（理由：200 节点不是瓶颈）——这个判断可能对，
   但既然把它作为省事的依据，就该留一条最低限度的量化断言兜住它，否则"不做"是无据的。
2. **"打开"的耗时**。§1.4 前提认知说"打开设置慢"的主因是启动解析 + render body 的同步 JSON.parse。
   注意这里有个错位：**启动解析发生在页面加载时，不在"点通用"时**。所以"点开通用慢"的真实成本
   只剩 G5（parse）+ G6（DOM），两个都治了，很好——但没有一条口径**直接测这个动作的耗时**。
   节点数 ≤10 不等于打开快。

**怎么改**。补两条，都放在 T4.3 手工验收里（不做门禁，和 P9 同级即可）：
- **P10**：`performance.mark` 测从点击"通用"到设置页可交互的耗时，与"卸载本插件后"的同一测量对比，
  差值 ≤ 一个在 T0 阶段实测基线后落定的阈值。
- **P11**：面板打开且 `section='skin'`（卡片最多）时，用 S3 那套 rAF 采样测面板内滚动 60 帧 p95，
  与面板关闭时对比。这条同时给"不做虚拟化"这个决策提供证据；若超标，虚拟化再谈。

### I10 — 旧包共存时同一批 storage 键被两套逻辑读写，R6 的"外观错乱"低估了，且缺一条 5 行的防线

**位置**：§5 R6 失败模式 1（第 543-544 行）、§1.1 D2、§1.1 D5

**问题**。D2（换新槽位 id）+ D5（零迁移、8 键原样沿用）这个组合有个副作用没被算进去：
换 id 保证了不会启动 throw，但**零迁移意味着新旧包共用同一批 storage 键**。
旧包忘卸时，两套完整逻辑（各自的 subscribe/notify、各自的启动恢复、各自的引擎）
在同一批键上并发读写。R6 把后果描述为"设置页多出两个旧入口 + 外观错乱，刷新/卸旧包即恢复"。

"刷新即恢复"这句需要打个问号：两个引擎都做启动恢复、都 `activateSkin`、
body 属性与内联 style 双写，**刷新只会把同一个状态再复现一遍**，不是恢复。
真正恢复要靠卸旧包。而且这个状态下用户操作 UI 会让两套逻辑交替写键，
写坏的概率不为零（§3.5 的软互斥能拦住 track 键被抢占，这是运气好，不是设计）。

R6 的缓解手段只有三条：新 id 不 throw ✓、README 迁移段写在最前、T4.3 加一个"三包共存能启动"场景。
中间那条基本无效——没人读 README。

**怎么改**。加一条**运行时自检**，代价约 5 行：新包 `apply(ctx)` 时检测旧包在场
（最省事的探针：旧包注入的 `<style>` 标记，或旧槽位 id 是否已注册），
在场则在 E1 摘要位置渲染一行醒目提示：「检测到旧版 theme-gallery / skin-gallery 仍已安装，
请先卸载，否则外观会冲突」。这比文档有效一个数量级，且顺手给 T4.3 那个共存场景提供了断言目标。
把这条写进 §3.3 E1 的契约里。

### I11 — E1 摘要在"悬空 applied"时显示什么，未定义

**位置**：§3.3 E1（第 213 行）、§3.2 启动恢复（第 203 行）

**问题**。§3.2 已经想到了悬空的情况：「若 `theme-gallery-custom-applied-v1` 指向**存在的**自定义主题
→ 应用它；**否则**应用 family」。也就是说 applied 键可能指向一个已不存在的 id
（用户手动清了 registry、或跨设备同步了一半、或 registry JSON 损坏按空处理——§3.8 第 6 条正好制造这个状态）。

但 E1 摘要的契约只写了三种文案：`精选主题 · <label>` / `完整皮肤 · <name>` / `默认外观`。
悬空时 `label` 取不到，摘要显示什么？空字符串？`undefined`？还是回落到实际生效的 jade？

这是个小问题，但它出现在**用户打开设置第一眼看到的那行字**上，而且 §3.8 第 6 条（registry 损坏容忍）
把这个状态设计成了"可以正常发生"的状态，不是异常。

**怎么改**。E1 补一句：摘要**只反映实际生效的外观**（与 §3.2 启动恢复的判定结果一致），
不直接读 applied 键渲染文案。也就是 applied 悬空时显示 `精选主题 · 竹青`（jade），
和用户眼睛看到的一致。补一条断言：预置悬空 applied → 摘要文案 = jade 的 label。

### I12 — 错误文案含用户可控内容，渲染方式未约定

**位置**：§3.8 开头（第 359 行）、§3.7 校验顺序第 10 条（第 349 行）

**问题**。§3.8 说「UI 统一渲染 `${code}: ${message}`」，但没说**怎么**渲染。
而 message 里有用户可控内容：§3.7 第 10 条明写 `ERR_SKIN_CONTRACT` 的
「message 含第一个违规名」——这个违规名是从用户粘贴的 `client.js` 文本里正则抓出来的。
若实现用 `innerHTML` / `dangerouslySetInnerHTML` 渲染错误条，这就是一条从"粘贴文本"到 XSS 的完整路径，
而且它在**校验失败**的分支上——恰好是所有人以为"已经拦住了"的地方。

React 默认的 text child 是安全的，所以这大概率不会出事。但"大概率"不该出现在
唯一的测试输入文档里对一个注入面的处理上。

**怎么改**。§3.8 加一句硬约定：「错误文案只作为 React text child 渲染；
`src/**` 中**不得出现** `dangerouslySetInnerHTML` / `innerHTML` / `insertAdjacentHTML`（一条静态断言）。」
一行断言，永久闭合这个面。这条断言顺带也覆盖了皮肤卡片里其它渲染用户内容的地方（name / author / tagline）。

## 建议（可选）

### S1 — 砍掉 section 懒挂载这一层

**位置**：§1.2（第 38 行）、§3.3（第 217 行）

`open` 这一层已经把 15+9 张卡挪出首屏了。再加一层"一次只挂载一段"，买到的是
"打开面板后少挂 100 个节点"，代价是：多一个 state、切段时搜索词/勾选态丢失（需要额外契约说明）、
以及 I1 那个试穿态问题多一个触发路径（切段也会卸载面板段）。

而 §1.4 自己判定"200 节点不是瓶颈"（不做虚拟化的理由）。同一个判断应该也适用于分段——
**不能一边说 200 节点不值得虚拟化，一边为了 100 节点加一层懒挂载**。

建议：视觉上保留"主题区 / 皮肤区"两个分区（BRIEF 要的是这个），但两段同时挂载，删掉 `section` state。
若 I9 补的 P11 实测显示面板内滚动真的卡，再加回来——那时有数据支撑。

### S2 — T4.2 的幂等断言在旧包删除前必然是脏的

**位置**：§4 T4.2（第 487 行）、§4 T4.4（第 489 行）

T4.2 要求「跑根 `pnpm -r build` 与 `pnpm -r check`，之后 `git status` 里 `lib/client.js` 无改动」，
但 T4.2 排在 T4.4（删旧包）**之前**。此时旧三包还在，§4.2 那个"check 先写盘"的地雷在旧包里没修，
`pnpm -r` 会把旧包的产物搞脏 → T4.2 必红，且不是新包的问题。诊断成本白花。

建议：T4.2 拆两步。T4.2a（删包前）：`pnpm --filter dsh-appearance-gallery build && check`，
`git status` 只看 `packages/appearance-gallery/`。T4.2b（挪到 T4.4 之后）：根 `pnpm -r` 全量幂等。
后者才是 BRIEF 硬约束真正要的那个证明。

### S3 — storage 键白名单断言的路径范围漏了 `skins/**`

**位置**：§3.4 第 5 条（第 267 行）、§5 R11 第 3 行

白名单断言限定在 `src/**`。但 9 套内置皮肤的 `client.js` 在 `skins/**`，不在 `src/**` 里，
而它们是会被内联进产物并执行的真实代码。导入路径靠 12 条黑名单拦住了 `localStorage`，
**内置皮肤没有任何等价检查**。

建议：把断言路径扩到 `skins/**`（P1 已经在 grep 这个目录，顺手的事）。
这不是怀疑内置皮肤，是让"只碰 8 个键"这个承诺的断言范围与承诺本身对齐。

### S4 — 两份 6 行记忆化的重复，可以不抽但要留痕

**位置**：§1.4 G5（第 64 行）、§4 T3.1（第 478 行）

`custom-theme.js` 和 `custom-skin.js` 各写一份按 raw 比对的记忆化。集合是封闭的（就 2 个 registry，
不会持续新增），所以枚举没问题，**不需要抽公共 helper**——抽了要新增文件 + 改 build.mjs 拼接顺序，
不划算。但两处逻辑必须一致（不一致就是"一边有缓存一边没有"这种偶发差异）。

建议：不抽，但 P6 单测对 theme 和 skin **两侧各跑一遍**（当前 P6 只写了 `getSkins()`），
两边都被断言覆盖，就不怕改一边忘一边。

### S5 — T1 搜索框的超长输入

**位置**：§3.3 T1 / S1（第 223、235 行）

两个搜索框都标"无失败路径"。纯前端 `toLowerCase().includes()` 确实不会失败，
但用户粘贴一段几十 KB 的文本进去，每次 keystroke 对 24 个条目做一次长串 includes——
不会崩，但 §1.4 特意提了"搜索框每敲一个字触发一次"是 G5 要治的场景之一。

建议：搜索词截断到 64 字符（一行代码），并在契约里写明。不值得单独测。

## 四维度核对结果

| 维度 | 结论 |
|---|---|
| **正确性** | 错误契约的**导入路径**（§3.6 主题 8 条、§3.7 皮肤 12 条，含短路顺序）是本方案质量最高的部分，测试可直接照写，无缺漏。**缺口在导入之外**：a11y 参数无契约（I5）、引擎 null 时 S5/S7/S8 未定义（I6）、覆盖同 id 已应用皮肤未定义（I7）、E1 悬空 applied 未定义（I11）。边界场景里"空/0/超长"基本覆盖（`tokens` 空对象、`label` 超 80、256 KB 上限都写了），**"并发/重复操作"整块缺失（I4）**，"重复导入同 id"写了但漏了已应用那一支（I7）。状态与数据流最大的漏态是试穿态在面板卸载时的归属（I1）。 |
| **安全** | BRIEF 敏感面三项在 R11 里逐项对了表，态度是对的，但**第 1 项（不新增外部网络请求）的保证范围小于其措辞**——只审自家代码，没覆盖用户导入的 a11y CSS 可经 `@import` / `url()` 发请求（I5）。信任边界未声明：导入 bundle 是同源全权限经典脚本，12 条黑名单是防手滑不是沙箱，方案却把它列为"保证手段"（I5）。注入面还有错误文案渲染方式未约定（I12）。**实现路径本身不高危**：不改系统组件、不 hook 他人进程、不绕平台安全机制、不写项目外目录（navigation-diary 明确标注"只读引用，不搬进仓库"，处理得当）。localStorage 白名单 + 禁遍历这条设计是对的，只是路径范围漏了 `skins/**`（S3）。 |
| **性能** | 治理手段对准了资源侧（G1/G2/G3）和渲染侧（G5/G6），方向正确，G5 选"按 raw 比对而非写时失效"这个判断很扎实（顺带解决跨标签页脏读）。但**验收口径兜不住 BRIEF 的原话场景**：没有一条测"打开设置的耗时"和"面板打开后滚动"（I9）。更严重的是 G1 的论证矛盾（F1）——它可能整条落空而所有自动化门禁照样绿。体积门禁数值状态未定（I3）。架构层没有其它明显低效设计。 |
| **可维护性** | **过度设计**：`section` 懒挂载多余（S1）、`lib/invariant.js` 与 `src/index.js` 的空占位需要给出存在理由否则砍掉（I8）。方案主动砍掉虚拟化和 `React.memo` 大扫除、拒绝建 `src/ui/` 二级目录、拒绝写 storage 迁移代码，这几个"不做"的决策都判得对，值得保留。**抽象不足**：没发现该抽没抽的——12 条黑名单虽是枚举且集合其实开放（新 API 会持续出现），但它是冻结的对外契约，此处只能声明已知边界（I5），不能改成开放机制。两处记忆化重复属可接受枚举（S4）。**模块拆分合理**：client → panel → api 单向依赖，无循环，D4 工厂化的理由（拼接作用域重名）是真实约束不是品味。唯一的边界模糊是引擎归属（I1）与 deps 契约缺失（I2）。 |

### 必查项回执

1. **§3 错误契约完整性**：导入类（T3/S7）完整且优秀；**缺 5 处**——a11y 参数（I5）、
   引擎 null 下的 S5/S7/S8（I6）、覆盖已应用同 id（I7）、E1 悬空 applied（I11）、
   并发重复调用（I4）。已判"重要"。
2. **未验证假设与 spike**：方案的 spike 意识是加分项，5 条假设都标了（S1/S2/S4/S5 归属清楚，
   S3 定位偏了）。但**S1 的实验方法证实/证伪的不是 G1 依赖的那个假设**——
   它测"滚动容器在哪"，而 G1 需要的是"fixed 背景是否为滚动卡顿主因"，两者不等价，
   且在其中一个分支下 G1 收益为零而方案无预案。已判**致命 F1**。
   另有一处未标 spike 的假设：G3 的"WebP 重编码能把 773 KB 压到 300 KB"是估算而非实验结果
   （I3 第 3 条），建议在 T3 之前先拿一张图试压 10 分钟，再定门禁。
